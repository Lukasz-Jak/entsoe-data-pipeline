# ADR-004: Add optional PostgreSQL storage for actual generation

**Status:** Accepted  
**Date:** 2026-06-13  
**Scope:** Optional PostgreSQL storage for `actual_generation`

## 1. Context

The `actual_generation` dataset is more complex than `total_load` because it
contains many production types and measurement types.

The file output remains wide for CSV/XLSX compatibility, with one column per
generation series. PostgreSQL storage needs to support flexible analytical
queries across production types, measurement types, intervals, and dates.

PostgreSQL remains an optional extension. The existing file-based workflow must
remain valid and unchanged.

## 2. Decision

The project will keep PostgreSQL optional and separate from the main pipeline.

The selected design is:

- Import existing CSV/XLSX outputs using a dedicated script.
- Store actual generation data in `entsoe_raw.actual_generation`.
- Use a long/narrow model instead of a wide PostgreSQL table.
- Use `timestamp_utc`, `country_code`, `interval_minutes`, `production_type`, and `measurement_type` as the logical key.
- Preserve the original input column in `source_column`.
- Normalize `production_type` for SQL-friendly analytical use.
- Keep `measurement_type` separate from `production_type`.
- Reject legacy ambiguous columns without suffixes instead of guessing their meaning.
- Add a daily mart view in `entsoe_mart`.
- Add a read-only validation SQL script.

Rejected alternatives:

- A wide PostgreSQL table with one column per production type was rejected because it would require schema changes when production types change.
- Guessing `measurement_type` for old files was rejected because ambiguous source columns can lead to incorrect data semantics.
- Direct pipeline-to-database writes were rejected at this stage to keep PostgreSQL separate from the main ingestion workflow.
- Introducing a migration framework was rejected because version-controlled SQL scripts are sufficient for the current scope.
- Building a full warehouse or orchestration layer was rejected because it is outside the project scope.

## 3. Consequences

- The existing file workflow remains unchanged.
- The raw table can support new production types without schema changes.
- The design is better for filtering, grouping, and aggregating by production type.
- The `source_column` field preserves traceability to the original file.
- Some older generated files must be regenerated before import.
- Future direct API-to-PostgreSQL writing can reuse the same wide-to-long mapping logic.
