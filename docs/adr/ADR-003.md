# ADR-003: Add optional PostgreSQL storage for total load

**Status:** Accepted  
**Date:** 2026-06-13  
**Scope:** Optional PostgreSQL storage for the `total_load` dataset

## 1. Context

The original project is a local CSV/XLSX ENTSO-E ingestion pipeline. Its primary
workflow downloads selected datasets and persists deterministic local file outputs.

PostgreSQL was added as an optional storage extension. The existing file-based
workflow must remain valid and unchanged.

The `total_load` dataset was selected as the first PostgreSQL-backed dataset
because it has a simple and useful time-series structure with actual and forecast
load values.

## 2. Decision

The project will keep PostgreSQL optional and separate from the main pipeline.

The selected design is:

- Import existing CSV/XLSX outputs into PostgreSQL using a dedicated script instead of writing directly from the pipeline.
- Store raw total load data in `entsoe_raw.total_load`.
- Use `timestamp_utc` as the canonical time column.
- Store both hourly and 15-minute data in one table using `interval_minutes`.
- Use `country_code`, `timestamp_utc`, and `interval_minutes` as the logical key.
- Use idempotent upsert behavior to avoid duplicate rows when importing the same files again.
- Add a mart/summary view in `entsoe_mart` for daily analysis.
- Add a read-only SQL validation script for manual post-import data-quality checks.

Rejected alternatives:

- Replacing CSV/XLSX output with database-only storage was rejected because the file-based workflow remains the primary project behavior.
- Direct pipeline-to-database writes were rejected at this stage to avoid coupling the main ingestion flow to PostgreSQL.
- Introducing a migration framework such as Alembic was rejected because version-controlled SQL scripts are sufficient for the current scope.
- Building a full warehouse or orchestration layer was rejected because it is outside the project scope.

## 3. Consequences

- The existing file-based pipeline remains unchanged.
- PostgreSQL can be reproduced from version-controlled SQL scripts.
- Existing outputs can be imported without redownloading data.
- The design supports both hourly and 15-minute data.
- The mart view provides a simple analytical layer.
- The validation script improves confidence in imported data.
- Future datasets can follow the same pattern, but should be added deliberately and documented separately if needed.
- Some duplication remains between file outputs and database storage, but this is acceptable because PostgreSQL is optional.
